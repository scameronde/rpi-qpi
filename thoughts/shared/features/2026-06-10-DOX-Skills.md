# Feature Brief: DOX Skills — dox-init and dox-update

## System Context

**Project**: rpiqr — Agentic Engineering Framework for Claude Code  
**Core purpose**: A structured workflow framework that provides Claude Code with a pipeline of Skills and Agents to take a software idea from mission → spec → epics → research → plan → implementation. Skills are user-invokable (via `Skill` tool / `/skill-name`); Agents are worker bots spawned by Skills.  
**Relevant existing components**:
- `.claude/skills/` — all skill SKILL.md files (the extension point for this feature)
- `CLAUDE.md` — root governance; already contains a DOX Protocol section (lines activating DOX pre-/post-edit traversal)
- Existing partial DOX tree: `AGENTS.md` files already present at `thoughts/shared/`, `thoughts/shared/plans/`, `thoughts/shared/research/`, `thoughts/shared/qa/`, `.claude/agents/`
- Research: `thoughts/shared/research/2026-06-09-DOX-Framework-Integration.md` — full DOX analysis and four integration approaches documented

## Feature Vision

DOX (https://github.com/agent0ai/dox) is a hierarchical governance protocol: `AGENTS.md` files distributed across the filesystem act as local contracts for agent behavior in their subtrees. The framework already activated DOX in `CLAUDE.md` and partially populated the tree, but the initialization and ongoing maintenance of the DOX tree is currently a manual, open-ended obligation.

The gap: there is no reliable way to bootstrap a complete DOX tree for a new project or to detect and repair an incomplete or stale tree in an existing project. Developers using this framework who want DOX governance must manually inspect every directory, write each AGENTS.md from scratch, and maintain them as the codebase evolves.

Two new skills close this gap: `/dox-init` bootstraps the complete DOX tree in one shot; `/dox-update` keeps it current autonomously over time. Together they turn DOX from a passive protocol into an active, maintainable layer of the framework.

## Target Users

**Primary users of this feature**:
- Developers using this framework in their own projects who want DOX governance from the start
- The framework maintainer (the user) managing the rpiqr project's own DOX tree

**Impact on other users**: None — both skills are invoked explicitly and are purely additive.

## Feature Value Proposition

Users can establish and maintain a complete, accurate DOX governance tree with a single skill invocation instead of manually writing and updating AGENTS.md files across every directory.

## Essential Capabilities

1. **`/dox-init` — Bootstrap the DOX tree**
   - **What it enables**: A developer can run one skill in a project that has no AGENTS.md files and get a complete, populated DOX governance tree. This includes: a root `AGENTS.md` containing the DOX protocol, an updated `CLAUDE.md` with the DOX reference section, and an AGENTS.md for every relevant directory in the project tree.
   - **Why it's essential**: Without a bootstrap capability, the barrier to DOX adoption is per-directory manual effort. Init makes DOX a one-command decision.

2. **`/dox-update` — Detect and repair stale AGENTS.md files**
   - **What it enables**: A developer can run one skill to identify all AGENTS.md files whose content no longer accurately describes their directory (new files added, files moved, purpose changed) and have them regenerated autonomously.
   - **Why it's essential**: DOX trees decay as projects evolve. A stale AGENTS.md is worse than none — it misdirects agents. Update makes DOX maintenance continuous rather than a one-time snapshot.

3. **AI-driven content generation per directory**
   - **What it enables**: Each AGENTS.md is generated by analyzing the actual contents of the directory — file names, existing documentation, patterns — not from a generic boilerplate. The resulting AGENTS.md accurately reflects Purpose, Ownership, Local Contracts, Work Guidance, Verification, and Child DOX Index for that specific directory.
   - **Why it's essential**: A generic template applied to every directory provides no value and adds noise. The DOX protocol's proximity principle (closer docs are more specific) only works if child docs are genuinely tailored.

4. **Fully autonomous execution (no per-directory confirmation)**
   - **What it enables**: Both skills scan the directory tree, make all writes, and report results at the end — no intermediate prompts. The user reviews the written files after the fact.
   - **Why it's essential**: A skill that asks "shall I write this AGENTS.md?" for 30 directories is not usable in practice. Autonomy is the prerequisite for the feature being worth invoking.

## Explicit Non-Goals

- **Full DOX migration of CLAUDE.md**: Moving governance content from `CLAUDE.md` into the DOX hierarchy is explicitly out of scope. CLAUDE.md remains the primary Claude Code instruction file. DOX supplements it.
- **Modifying up-to-date AGENTS.md files during dox-update**: If an existing AGENTS.md accurately reflects its directory's current state, it is not touched. Update is a repair operation, not a regeneration of everything.
- **DOX compliance enforcement during other skills**: The implementer-prompt already has both DOX protocols wired in (pre-edit read traversal at step 1, post-edit AGENTS.md update at the self-review checklist). These two skills do not modify other skills.
- **Supporting non-Claude-Code agent platforms**: The skills are implemented as Claude Code SKILL.md files and are not designed for portability to other agent platforms.
- **Interactive per-directory review or approval**: The "propose then confirm" flow is explicitly excluded in favor of full autonomy.

## Inherited Constraints

**Technology Stack**:
- Skills are SKILL.md Markdown files in `.claude/skills/<skill-name>/SKILL.md`
- Invoked via the Claude Code `Skill` tool (registered under the skill name, not a separate CLI)
- Skills may use: `Read`, `Write`, `Edit`, `Bash` (for directory traversal and file listing), `Agent` (to spawn codebase analysis agents), `AskUserQuestion` (for pre-flight scope clarification if needed)
- No external dependencies — skills are pure Markdown instruction files

**Architectural Constraints**:
- The DOX child AGENTS.md schema is fixed: Purpose → Ownership → Local Contracts → Work Guidance → Verification → Child DOX Index (omit sections that don't apply)
- The root AGENTS.md must contain the verbatim DOX protocol (from https://raw.githubusercontent.com/agent0ai/dox/main/AGENTS.md) as the standard installation method
- Existing AGENTS.md files that are accurate must not be clobbered by dox-init (it is additive/idempotent, not destructive)
- `CLAUDE.md` already has a DOX Protocol section; dox-init must not duplicate it — it should verify the reference is present and add it only if missing

**Operational Constraints**:
- Skills operate on the current working directory (the project Claude Code is running in)
- Certain directories are excluded from the DOX tree: `.git/`, `node_modules/`, `dist/`, `build/`, `__pycache__/`, and other auto-generated or tool-managed directories
- A directory merits an AGENTS.md only if it contains meaningful files (not empty, not containing only auto-generated artifacts)

## Integration Points

- **`.claude/skills/` structure**: Both skills add a new subdirectory (`dox-init/SKILL.md` and `dox-update/SKILL.md`) exactly like all other skills. Root `AGENTS.md`'s Child DOX Index for `.claude/skills/` must be updated to reference these two new skill directories.
- **`CLAUDE.md` DOX Protocol section**: `dox-init` verifies this section exists and adds it if missing. It does not modify or relocate the section if present.
- **Existing AGENTS.md files**: Both skills must read existing AGENTS.md files before writing — `dox-init` to detect what's already present and skip it, `dox-update` to compare against actual directory state.
- **`codebase-locator` agent**: Both skills can spawn `codebase-locator` to enumerate directory trees and identify relevant directories rather than relying on raw Bash find commands.
- **`web-search-researcher` or direct WebFetch**: `dox-init` needs the canonical DOX AGENTS.md content; it may fetch it from `https://raw.githubusercontent.com/agent0ai/dox/main/AGENTS.md` or use a bundled snapshot.

## Success Criteria

From a user perspective, this feature is complete when:

- [ ] Running `/dox-init` in a project with no AGENTS.md files produces a root `AGENTS.md` containing the DOX protocol, a `CLAUDE.md` DOX reference section (if missing), and an `AGENTS.md` in every meaningful directory in the project tree
- [ ] Running `/dox-init` in a project that already has some AGENTS.md files leaves existing, accurate files unchanged and only creates the missing ones (idempotent)
- [ ] Running `/dox-update` identifies all AGENTS.md files that no longer accurately describe their directory and regenerates only those files
- [ ] The generated AGENTS.md content for each directory is specific and accurate — it describes that directory's actual files, purpose, and conventions, not generic boilerplate
- [ ] Both skills produce a summary report at the end: which directories were created/updated and which were skipped

## Assumptions

**About the existing system**:
- Claude Code reads `AGENTS.md` files in subdirectories as part of its context loading (confirmed by DOX README claim; empirical validation assumed to have occurred before implementation)
- The DOX protocol schema (the six-section child shape) is stable enough for implementation; the project is 8 days old and may have breaking changes
- `Bash` with `find` is sufficient for directory traversal in skill implementations; no special filesystem permissions are needed

**About users**:
- Users will review the generated AGENTS.md content after both skills complete — the skills are not expected to produce perfect first-draft governance docs, but good enough drafts that require light editing
- Users understand that `dox-update` may regenerate manually-edited AGENTS.md files if the AI analysis determines they are stale; this is acceptable

## Open Questions for Researcher

Before planning implementation, the Researcher should investigate:

- [ ] **How do existing skills handle long multi-directory operations?** Check if any skill already loops over directories and writes multiple files — that pattern is the model for both DOX skills.
- [ ] **What is the full current DOX tree state?** List all directories that already have AGENTS.md files vs. all directories that should have them — this is the gap that dox-init would close in the rpiqr project itself.
- [ ] **How should the skills handle the root AGENTS.md content?** Should they fetch the canonical DOX AGENTS.md from GitHub at runtime (network dependency) or bundle a snapshot as a template inside the skill? Explore the tradeoffs.
- [ ] **What exclusion list is appropriate for this framework?** Confirm which directories (auto-generated, vendor, hidden) should be skipped and verify that against the current directory structure.
- [ ] **Does the `codebase-locator` agent return enough structural information** (directory hierarchy, file counts, file names) to support AI-driven AGENTS.md generation, or does the skill need to spawn a different agent type or use direct file reads?

## Conversation Summary

- **Initial idea**: Add two new skills (or agents or commands) for DOX tree initialization and update; user unsure of the right primitive
- **Refinements**: Confirmed skills (not agents) since they are user-invokable operations; confirmed "two separate skills" over a combined command; confirmed AI content analysis for staleness detection over simpler heuristics; confirmed fully autonomous execution
- **Key boundary decisions**: Full DOX migration of CLAUDE.md is explicitly out of scope; dox-init is idempotent (does not overwrite accurate existing files); DOX closeout wiring into other skills (like implementer-prompt) is a separate feature
