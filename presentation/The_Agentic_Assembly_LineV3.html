ORBIT V3
Engineering braucht Ordnung, keine Chaos
Die Fehler unstrukturierter KI-Entwicklung ('Vibe Coding') im Kontrast zum disziplinierten, stufengesteuerten Erfolg des ORBIT agentischen Frameworks.
Zusammenfassung: Agentisches Software-Engineering ersetzt unstrukturiertes KI-Prompting durch eine Pipeline spezialisierter Agenten. Durch die Durchsetzung der "Goldenen Regel", nach der kein Agent einen Schritt überspringt, stellt das ORBIT-Framework sicher, dass jede Zeile Code auf eine spezifische Vision und einen verifizierten technischen Plan zurückverfolgbar ist.
Vibe Coding (Das Chaos)
Halluzinationen
Direkt zur Implementierung zu springen führt ohne Einschränkungen zu falscher oder imaginärer KI-Logik.
Scope Creep
Fehlende Grenzdefinition lässt Projekte unkontrolliert wachsen, ohne das Kernproblem zu lösen.
Kontextverlust
Unverbundene Prompts lassen die KI die ursprünglichen Anforderungen und Designentscheidungen aus den Augen verlieren.
ORBIT-Architektur (Die Ordnung)
AUSFÜHRUNG Den verifizierten Plan implementieren. PLANUNG Die Codebasis zuerst kartografieren, damit jede Aufgabe durch verifizierte Befunde belegt ist. SPEZIFIKATION Die technische Architektur definieren, bevor eine Technologie gewählt wird. VISION Das "Warum" definieren, bevor eine Technologie oder ein Framework gewählt wird.
Die Goldene Regel: Kein Agent überspringt einen Schritt. Jede Phase setzt das Artefakt der vorherigen Phase voraus.

Das Herzstück von ORBIT: Die Artefakt-Kette
ORBIT ist keine Sammlung von Befehlen — ORBIT ist eine Kette von Dokumenten.
Jeder Skill ist eine Transformation
Jeder Skill liest das Artefakt der vorherigen Phase und erzeugt das Artefakt für die nächste. Die Informationsdichte steigt mit jedem Schritt: von abstrakter Vision zu konkretem, ausführbarem Quellcode.
Alle Artefakte leben in: thoughts/shared/
Jedes Artefakt referenziert seinen Vorgänger — ein lückenloses Audit-Log von der User Story bis zum Git-Commit.
Die Ausnahmeregel
Die /mission-architect und /feature-architect Skills lesen kein Artefakt — sie starten die Kette aus einem Gespräch mit dem Nutzer.
Alle anderen Skills folgen der Regel: Ein Eingabe-Artefakt rein, ein Ausgabe-Artefakt raus. Kein Skill überspringt einen Schritt. Das Ende der Kette ist kein Dokument — es ist ausführbarer Code.

Das DOX-Framework: Jedes Verzeichnis hat einen Vertrag
Kein Installations-Paket. Keine Abhängigkeiten. Nur AGENTS.md-Dateien — direkt dort, wo die Arbeit stattfindet.
Was sind AGENTS.md-Dateien?
Hierarchische Governance-Verträge für Verzeichnis-Teilbäume. Die Root-AGENTS.md setzt projektweite Regeln; jede Child-AGENTS.md konkretisiert sie für ihre Domäne. Je näher eine AGENTS.md an der bearbeiteten Datei liegt, desto stärker gilt sie.
Nähe-Regel: Die nächste AGENTS.md zur Zieldatei ist der lokale Vertrag. Eltern-AGENTS.md liefern übergeordnete Regeln. Keine AGENTS.md darf CLAUDE.md überschreiben.
Das Protokoll: Zwei Pflichten
Vor jeder Dateiänderung — Lesen:
Vom Repository-Root bis zur Zieldatei jeden Verzeichnisebene prüfen und vorhandene AGENTS.md einlesen.
Nach einer bedeutsamen Änderung — Schreiben:
Wenn Zweck, Struktur, Ownership oder Konventionen eines Verzeichnisses betroffen sind, die nächste AGENTS.md aktualisieren.
/dox-init
Governance-Baum bootstrappen
Einmalig bei Projektstart. Erzeugt Root-AGENTS.md und eine Child-AGENTS.md für jedes bedeutungsvolle Verzeichnis. Idempotent — überschreibt nie bestehende Dateien.
/dox-update
Veraltete Verträge reparieren
Nach größeren Codeänderungen. Prüft jede AGENTS.md gegen den aktuellen Verzeichnisinhalt — veraltete Dateien werden regeneriert, aktuelle bleiben unberührt.
DOX ist kein Pipeline-Schritt — es ist die Governance-Schicht, die alle Pipeline-Schritte umhüllt. Aktiv bei jedem Datei-Edit, besonders während /implement.
